Package Tracking Platform

Scan events flow from Kafka through Spark Structured Streaming. Spark keeps the current status of every package in Postgres and appends all raw history to Parquet. Hourly batch jobs turn that history into delivery and facility analytics, and every step reports to Prometheus.

Upstream to downstream

One scan event, end to end

  1. A scanner emits an event

    The generator plays devices across the network: CREATED, PICKED_UP, ARRIVED_AT_FACILITY, DELIVERED and more. It injects duplicates, late and out-of-order events, and malformed payloads on purpose. It also records what the platform should end up with (the manifest).

    t = 0

  2. Kafka stores it in order per package

    Topic package-events.v1 uses the package ID as key, so all events for one package land in one of 6 partitions, in order. Kafka stamps the ingest time (LogAppendTime). The topic keeps 7 days, which is the window for restarting without data loss.

    ms

  3. Spark reads it twice, in parallel

    One driver runs two streaming queries over the same topic, each with its own checkpoint. Query A maintains status. Query B archives every record. Neither waits for the other.

    each micro-batch

  4. Query A validates and routes

    processor-core checks the JSON against contract v1. Failures get one of 14 error codes, for example INVALID_TIMESTAMP or UNKNOWN_EVENT_TYPE, and go to the DLQ topic with the raw payload and source offset. Valid events are deduplicated by event_id within a 2-hour watermark.

    seconds

  5. Postgres applies it, idempotently

    Per Spark partition, one transaction inserts event IDs into tracking.processed_events. Only IDs that are new count. It then upserts tracking.package_status with a preference guard: a terminal event beats a non-terminal one, and otherwise the later event wins. Replays and retries cannot double-count or move a status backwards.

    seconds

  6. Query B appends it to bronze

    Every record, valid or not, is written to lake/bronze/package_events as Parquet, partitioned by ingest_date, with an is_valid flag. Bronze is never edited and is the source for every rebuild.

    seconds

  7. Silver deduplicates and compacts

    Hourly, lake_daily runs the silver build. It reads only bronze offsets newer than its watermark and rebuilds just the affected event_date partitions in a staging directory, then swaps them in. It keeps the earliest copy of each event, adds typed columns and a content hash, and compacts to one file per date.

    hourly

  8. Gold computes the KPIs

    Spark builds delivery facts and facility visits from silver, stages them in ops.gold_stage_*, then replaces the last 7 days of analytics.* in a single Postgres transaction. Readers never see a half-loaded window.

    hourly

  9. Data quality checks the result

    The DQ job runs DQ-02 to DQ-10: duplicates in silver, orphan packages, post-terminal scans, DLQ records with no bronze row, and more. Results go to ops.dq_results. A critical or high failure exits 1, so the Airflow run fails visibly.

    hourly

  10. People see it

    Status readers query tracking.package_status. Analysts run the query pack: on-time rate, delay percentiles, facility dwell, throughput and exception rate. Operators watch Grafana and the 8 Prometheus alert rules.

    any time

Delivery guarantees

What each hop promises

No hop claims end-to-end exactly-once. Each sink states its own guarantee, and each guarantee has a test that proves it.

Failure and recovery

What happens when something breaks

Processor restart

Resume from the checkpoint

Spark restarts at the last committed offsets and re-runs the open micro-batch. Events already applied are no-ops in processed_events. Nothing is lost while the outage is shorter than Kafka's 7 days.

make stream-down · make stream-up

Postgres down

The batch fails, offsets wait

The micro-batch fails without committing offsets. After Postgres returns, Spark retries the same batch, and the idempotent apply makes the retry safe.

Alert: PtpSinkFailures

Postgres data lost

Replay from bronze

replay_from_bronze reads bronze for a date range and applies it with the same processor-core rules as the stream. As-ingested mode reproduces the live decisions. Backfill mode lifts the age limit.

make replay FROM=… · Airflow: replay_from_bronze

Bad lake data

DQ stops the run

A critical DQ failure, such as a duplicate in silver, makes lake_daily fail at the dq task and fires PtpDqCriticalFailure. Rebuilding silver for that range fixes it, because bronze is unchanged.

make silver INGEST_FROM=… INGEST_TO=…
